## Post-run Analysis (2026-05-20)

This run produced a correct 100% diagnosis on a scenario the statistical screener was blind to. Three distinct mechanisms produced that outcome — only one of them involved a full RAG component. The analysis below disentangles them.

### Why the screener flagged nothing

Three things conspired to make this fault invisible to the statistical screener:

**The killed container's own metric vanishes (no anomalous value, no value at all).** Baseline shows `mongo: {'subscribers': 2}` collected via `mongosh`. Post-kill the source can't be reached, so `mongo`'s metrics block goes empty `{}` in the post-heal snapshot. ECOD's per-bucket models score the *features they have* against a *learned distribution* — a feature that disappears just isn't scored. There's no "subscribers dropped from 2 to NaN" signal, only an absence.

**MongoDB's primary dependents (UDR, UDM, AUSF) weren't being measured to begin with.** Look at the baseline:

```
udr   : baseline_keys=[]
udm   : baseline_keys=[]
ausf  : baseline_keys=[]
```

So even if these NFs had degraded in a measurable way after Mongo died, the screener couldn't have flagged them — they have no features in the trained feature space. Same failure shape as the cascading-IMS-failure runs from earlier this month: faults are invisible when the metric pipeline doesn't reach the affected NF.

**The NFs the screener CAN see (AMF/SMF/PYHSS) weren't being exercised against Mongo during the observation window.** Baseline vs post-heal:

- `amf`: `2 UE` → `2 UE` (no change)
- `smf`: `4 PDU` → `4 PDU` (no change)
- `pyhss`: `2 subs` → `2 subs` (no change)

The traffic agent's REGISTERs / VoNR calls don't directly query Mongo for these NFs in the live window — Mongo is the UDR backend, and UDR-mediated lookups happen at PDU-session-creation time. The synthetic traffic kept the existing 4 PDUs alive but didn't create new ones, so AMF/SMF metrics drifted ≤ noise floor.

**Net:** the screener honestly reported "nothing to see." The fault verifier *did* register a `confirmed` verdict with 4 nodes drifted (scscf/pcscf/icscf showing reduced traffic from the registration cascade collapse), but those drifts didn't cross ECOD's per-bucket significance thresholds. Same "fault below the feature-space resolution" failure class observed across cascading-ims-failure and now mongodb-gone.

### How the NA zeroed in on Mongo anyway

By **calling diagnostic tools directly**, not by reasoning from the (empty) screener output. The per-phase breakdown shows NA made 4 tool calls + 5 LLM calls — substantial activity for a phase that on screener-rich runs typically takes 2-3 tool calls. The tool-call trace is visible in the NA's layer-status `evidence` field:

| Tool | Returned | Triggered |
|---|---|---|
| `get_network_status()` | `'mongo': 'exited'` | The smoking gun |
| `get_network_topology()` | overall phase = `down` | Confirmed scope |
| `get_diagnostic_metrics(['udr','udm','ausf'])` | empty metrics for all three | Used as supporting evidence in h1 |

The NA's prompt allows direct diagnostic tool use when the screener is silent — that's the fallback path. Once `get_network_status` returned `mongo: exited`, the rest of the inference was mechanical: an exited container is a direct fault locus.

Critically, the IG's plan notes also flag a KB gap: "A `get_canonical_flows_through_component('mongo')` call returned no flows, indicating a potential KB coverage gap regarding these dependencies." So Mongo isn't actually in the flow-KB at all. The NA still correctly named UDR / UDM / AUSF as Mongo-dependent NFs from general knowledge of 5GC architecture, not from the KB. **Worth tracking as a separate KB-completeness gap** — the diagnosis succeeded despite the missing flow entry, but a future scenario where 5GC general knowledge is less reliable could leave the same gap as a load-bearing failure.

### Did RAG play a role?

The two halves of RAG (case retrieval vs. operational lessons) had **very different outcomes** in this run.

#### Case retrieval (Phase 2.5a) — zero role

> **Status:** `no_flags` — no_flags (corpus_size=102)
> *Phase 0 produced no anomaly flags, so the query couldn't be built — no retrieval ran.*

The retriever is keyed on screener flags. No flags = no query = no retrieval. The 11 prior `MongoDB Gone` cases sitting in the corpus never got fetched.

**This is a design gating choice worth flagging:** the runs where retrieval would arguably be most valuable (the NA has the least to go on, no screener signal to work with) are precisely the runs where retrieval is skipped. The corpus had fixture-perfect signal for this exact scenario and the pipeline didn't use it.

#### Operational lessons (Phase 2.5b) — meaningful, citable role

> **Cited lesson IDs:** `L10`

The citation detector caught L10 verbatim in h1's hypothesis statement:

> "The MongoDB container, a critical database for several core network functions, is the source of the failure because it has exited. **This is consistent with Operational Lesson L10.**"

And L10 itself:

> **L10 — Container "exited" status is a direct fault locus.** When `get_network_status()` lists a container as `exited`, that NF is the direct fault locus with very high prior. Investigate why it exited, not what's around it. Other components' degradations are downstream consequences.

That's the exact inference rule the NA applied. Without L10 it might still have reached the same answer (the connection is fairly obvious once `get_network_status` returns `exited`), but the rule is named verbatim in the structured output — citable, auditable, not implicit.

### Implications for next steps

Two design questions surface from this run, independent of one another:

1. **Case retrieval gating** — should the no-flags branch trigger an *alternative* retrieval path that builds a query from container status (`get_network_status` output) instead of screener flags? That would unblock retrieval for exactly the screener-blind runs where the agent is otherwise driving blind. Implementation cost: small (the retriever is already abstract over the query shape — needs a new query-construction code path keyed on `state["network_status"]` rather than `state["anomaly_flags"]`). Pre-condition: there'd need to be at least a baseline `get_network_status` call before NA runs — not currently the case, the orchestrator doesn't dispatch tools.

2. **NA's under-weighting of case retrieval** — this is the same pattern as the previous DPD post-fix run. The corpus has good signal and the NA doesn't use it. Two paths to address:
   - **Reweight the components:** drop case retrieval from NA-prompt influence, keep lessons. The empirical case for cases-as-currently-shaped earning their place is weak.
   - **Move case influence out of the LLM:** have RAG hits bias the Phase 6.5 candidate-pool promotion logic directly (a deterministic input rather than a soft-suggestion prompt block). The NA prompt would lose the `{prior_similar_episodes}` block; the candidate-pool aggregator would surface NFs that appeared as primary suspects in high-similarity prior cases as automatic promotion candidates.

Worth letting more runs accumulate before committing to either path. But the gating issue (#1) is independent and probably worth doing on its own — even if case retrieval is under-used by NA, having NO retrieval on the screener-blind path is a strict downgrade vs having some retrieval the NA might ignore.

### What this run is, in one sentence

A 100% diagnosis carried by **L10 + the NA's direct tool-call capability**, on a scenario where the screener, the path walker, the event aggregator, and case retrieval ALL produced zero signal. Lessons-injection earned its place; case retrieval's gating cost it any chance to contribute.
